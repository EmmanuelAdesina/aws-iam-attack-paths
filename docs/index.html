No CVE. No software exploit. Every stage uses legitimate AWS APIs against misconfigured trust relationships.

Hardcoded key in GitHub · CI/CD log leak · .env committed to repo

02 · Attack Surfaces

Four Entry Points, One Identity Graph

Each surface exploits a different layer of AWS authorization. Together they form the complete IAM attack surface.

sts:AssumeRole
Role Chain Exploitation
A low-privilege identity traverses trust edges to inherit progressively higher permissions. Each hop is a legitimate API call — only the chain is anomalous.
↗ Primary escalation path
iam:PassRole
Privilege Injection
An attacker with PassRole launches compute with a privileged role attached. Admin credentials are harvested from the Instance Metadata Service.
↗ Treat as AdministratorAccess
s3:GetBucketPolicy
Resource Policy Bypass
S3 bucket policies are evaluated independently of IAM identity policies. A wildcard principal exposes data regardless of role permission tightness.
↗ Bypasses IAM entirely
Cross-Account Trust
Organizational Pivot
A trust policy referencing an external account enables lateral movement across account boundaries. CloudTrail logs for this are split — correlation requires centralized logging.
↗ Org-wide blast radius
03 · Policy Analysis

Vulnerable vs. Hardened

The difference between a trust policy that invites escalation and one that doesn't is often a single line.

Vulnerable — Account-Root Trust 
"Principal": {
  "AWS": "arn:aws:iam::
    123456789012:root"
}

// Trusts every identity
// in the account.
// Compromise any one
// of them → role is yours.
Hardened — Specific Role + Condition 
"Principal": {
  "AWS": "arn:aws:iam::
    123456789012:role/
    CICDDeploymentRole"
},
"Condition": {
  "StringEquals": {
    "sts:ExternalId":
      "unique-id-2024"
  }
}
04 · Defense

Eight Questions That Define Your Attack Surface

If any answer is "I don't know," that gap is active attack surface.

01
Which identities have sts:AssumeRole on privileged roles?
// Map the in-edges to every high-privilege role
02
Can any low-privilege identity reach admin via role chaining?
// Enumerate multi-hop paths, not just direct assumptions
03
Where does iam:PassRole exist, and to which target role ARNs?
// PassRole is a tier-one escalation primitive
04
Which resource policies allow wildcard or external principals?
// IAM Access Analyzer finds these automatically
05
Are all cross-account trust relationships documented and reviewed?
// Cross-account pivots split CloudTrail evidence
06
Would you detect iam:UpdateAssumeRolePolicy at 2 AM?
// The persistence signal most teams miss
07
Would you detect a second access key added to an existing role?
// Key rotation does not remove attacker-created keys
08
Do your SCPs enforce what your IAM policies intend?
// IAM expresses intent; SCPs enforce invariants
