# IAM Trust Policy Examples
### From Vulnerable to Hardened — Four Patterns

> Trust policies define **who can become** a role.
> They are the most consequential and most overlooked component of IAM security.

---

## Pattern 1 — Account-Root Trust (Vulnerable)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:root"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**What this does:** Grants assumption rights to every IAM identity in account `123456789012` — every user, every role, every service.

**Why it is dangerous:** This is not a specific trust. It is account-wide access. If any identity in this account is compromised — a developer's access key, a misconfigured Lambda, a CI/CD credential — the attacker inherits this role.

**Common cause:** Auto-generated by AWS wizards or CloudFormation templates when a specific ARN is not supplied.

---

## Pattern 2 — Specific Role Trust (Recommended)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/CICDDeploymentRole"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

**What this does:** Grants assumption rights to exactly one role. Only the CI/CD deployment pipeline can assume this role.

**Improvement over Pattern 1:** Blast radius drops from every identity in the account to a single, specific role. Compromise now requires specifically targeting the pipeline.

**When to use:** Any automated system requiring cross-role access — CI/CD, monitoring agents, scheduled jobs.

## Pattern 3 — Role Trust with MFA Condition (Hardened for Human Access)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/SecurityEngineer"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "Bool": {
          "aws:MultiFactorAuthPresent": "true"
        },
        "NumericLessThan": {
          "aws:MultiFactorAuthAge": "3600"
        }
      }
    }
  ]
}
```

**What this does:** Allows the SecurityEngineer role to assume this role, but only if:
- The request is accompanied by a valid MFA token
- The MFA authentication occurred within the last 3600 seconds (1 hour)

**Why it matters:** Stolen credentials cannot be used to assume this role without also possessing the MFA device. The time condition prevents using an old MFA session — the attacker would need active, real-time MFA access.

**When to use:** Any role with access to production resources, sensitive data, or administrative capabilities when accessed by a human identity.

## Pattern 4 — Cross-Account Trust with External ID (Secure Multi-Account)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::222222222222:role/DeploymentRole"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "a7f3b2c1-prod-deploy-2024"
        }
      }
    }
  ]
}
```

**What this does:** Allows the deployment role in account `222222222222` to assume this role in the target account, but only when the correct External ID is provided.

**Why External ID matters:** Without an External ID, any identity that gains `sts:AssumeRole` in the trusted account — even legitimately — could assume your role. The External ID acts as a secret handshake. The trusted party must know it; random actors with legitimate access to the source account do not.

**When to use:** All cross-account role assumptions. This prevents confused deputy attacks where a third party is tricked into using their legitimate access to perform actions on your behalf.

## Threat Modeling Checklist for Trust Policies

Before finalizing any trust policy, confirm:

- [ ] Does the `Principal` reference a specific ARN, not `:root`?
- [ ] Is there a documented reason this trust relationship exists?
- [ ] If cross-account, is an External ID enforced?
- [ ] If human access, is MFA required?
- [ ] Is the trusted principal itself hardened (does it have its own tight trust policy)?
- [ ] Is this trust relationship in the quarterly access review scope?
- [ ] What is the blast radius if the trusted principal is compromised?

---

## The Question Trust Policies Answer

An IAM role's permission policy answers: *"What can this role do?"*

An IAM role's trust policy answers: *"Who can become this role?"*

Most security engineers spend their time on the first question. Attackers spend their time on the second.
